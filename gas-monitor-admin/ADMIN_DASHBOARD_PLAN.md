## 2. Architecture

Next.js admin UI in a 7-app monorepo (no workspace tooling — plain sibling
directories). The dashboard lives at `app/dashboard/*` behind a client-side
session check in `app/dashboard/layout.tsx`.

**Critical finding — the data layer is forked.**

- `lib/api.ts` `adminFetch()` calls `https://ugo.4fgmonitor.com/api/admin/*` —
  the standalone Express service `gas-monitor-backend`. **Every page uses this.**
- `app/api/*` (16 route files, ~700 lines) is a **byte-equivalent duplicate** of
  those backend routes, using the local Prisma client. **Nothing calls it.**
  `adminFetch` always prefixes `API_BASE_URL`, so these handlers are unreachable
  from the UI.

The duplicate is legacy from the backend being split into its own service (the
`.env.local` comment confirms: *"Standalone Express backend, now deployed on
Render"*). See §15.

## 3. Authentication

| | |
|---|---|
| Mechanism | Custom JWT, httpOnly cookie `admin_session`, 12h expiry |
| Signing | `jsonwebtoken`, `ADMIN_JWT_SECRET` |
| Login | `POST /api/admin/auth/login` — env root account **or** `admin_users` row (bcrypt) |

| Guard | Client-side `useEffect` in `app/dashboard/layout.tsx` → `/auth/me`, redirect to `/login` |
| Middleware | **None** (`middleware.ts` absent) |

**Will be reused unchanged.** No auth library will be added.

## 4. Authorization

Roles are real and ranked: `AdminRole = SUPER_ADMIN > OPERATIONS > SUPPORT`
(Prisma enum + JWT claim + `admin_users.role`).

Server-side enforcement **exists** in `gas-monitor-backend`:

| Guard | Location | Applied to |
|---|---|---|
| `requireAdmin` | `src/middleware/requireAdmin.ts:24` | stats, analytics, users, customers, vendors, listings, orders |
| `requireSuperAdmin` | `src/middleware/requireAdmin.ts:32` | all `/admin-users` routes |
| inline role check | `src/routes/admin/settings.ts` | `PATCH /settings` — SUPER_ADMIN or OPERATIONS |

**Gaps found (see §15 and the report):**

- `requireAdmin` does **not** distinguish SUPPORT from OPERATIONS. A SUPPORT
  admin can today approve vendors, delete users, and toggle listings — the UI
  simply never offered it. Adding richer UI without matching server checks would
  turn a latent gap into a live one.
- No audit trail exists for any of these actions (§8).

## 5. Database

Postgres (Supabase), Prisma 5.22. Schema at `prisma/schema.prisma`, **read-only
here** — `gas-monitor-web` owns migrations. 10 models, 7 enums.

## 6. API

| | |
|---|---|
| Style | REST, Express, `https://ugo.4fgmonitor.com/api/admin/*` |
| Client | `lib/api.ts` — `adminFetch(path, init)`, `credentials: 'include'` |
| Envelope | Per-resource key: `{ vendors }`, `{ orders }`, `{ listings }`, `{ users }`, `{ customers }`, `{ settings }`, `{ adminUsers }`. Stats/analytics return a bare object. |
| Errors | `{ error: string }` with 400/401/403/404/409 |
| **Pagination** | **None on any endpoint.** Hard `take: 200` on orders, listings, users, customers |
| **Search** | Only `GET /users?q=` (name/email, case-insensitive) |
| **Filtering** | Only `?status=` on vendors and orders |
| **Sorting** | None — always `createdAt desc` |

This is the single biggest constraint on the refactor. See §16 (Question 3).

## 7. Existing UI system

A coherent, custom design already exists and is **worth preserving**:

```
--accent      #2d7450   deep green (4FG brand)
--bg          #eef0ea   warm off-white
--card        #ffffff
--sidebar-bg  #0e2118   near-black green
--radius      10px / 7px / 14px
--danger      #b3413a   --warn/--clay #a9714c
font          Ubuntu
```

**What is good:** a real token block, a dark sidebar against a light canvas, a
restrained two-colour palette, `prefers-reduced-motion` already honoured.

**What is wrong:**

| Problem | Evidence |
|---|---|
| 83 hardcoded colour values outside `:root` | `grep -c` on `globals.css` |
| No semantic status colours | order/vendor status styled ad hoc per page |
| Per-page duplication | every page re-implements fetch + tabs + filter + table markup |
| **Wrong numbers on screen** | `orders/page.tsx:37` sums revenue over only the first 200 rows and labels it total; same in `vendors`, `listings`, `customers` |
| No loading state | pages render `null` until data arrives |
| No empty / error / forbidden states | a failed fetch renders a blank page silently |
| No pagination UI | the 200-row cap is invisible to the operator |
| No mobile strategy | one `@media (max-width: 900px)`; tables overflow |
| No URL filter state | filtered views cannot be shared |
| No dark mode | `color-scheme: light` only |

**Recommendation: refactor in place** — keep the brand, the routes, the auth,
and the API. Replace the per-page implementations with the resource engine.

## 10. Detected domain

**`marketplace`**, confidence **0.9**. Secondary: `ecommerce`.

Evidence: supply side (`VendorProfile` with an approval workflow + documents),
demand side (`User role=CONSUMER`), a catalog (`GasListing`), transactions
(`Order`), and a platform take (`PlatformSettings.platformFeePercent`).

Not `food-delivery` despite the delivery model: there is no courier/rider entity
and no delivery tracking. Not full `marketplace` either — there is no `Payout`
or `Commission` entity, so that module is skipped.

## 11. Recommended modules

| Module | Entity | Mode | Enabled | Dropped, and why |
|---|---|---|---|---|
| `orders` | `Order` | **reduced** | list, filter-status, search (client), detail, payment info | status-transition, cancel, refund, assign — **no write endpoint exists** |
| `vendors` | `VendorProfile` | **reduced** | list, filter-status, approval queue, documents, detail, performance | rejection reason (no field), suspend (no field), commission (no field) |
| `users` | `User` | **full** | list, search, filter-role, filter-status, detail, create, edit, delete, suspend | — |
| `customers` | `User role=CONSUMER` | reduced | list, spend/order aggregates, detail | create/edit — use Users |
| `products` | `GasListing` | **reduced** | list, filter-type, filter-stock, toggle stock, detail | create, edit, delete, images — no endpoints |
| `analytics` | aggregate endpoint | **full** | KPI row, revenue trend, status breakdown, vendor funnel, top vendors | date-range (endpoint is fixed at 6 months) |
| `settings` | `PlatformSettings` | **full** | general, fees, vendor signups, maintenance mode | — |
| `admin-users` | `AdminUser` | **full** | list, create, deactivate, reset password, delete | permission matrix — roles are an enum, not data |

### Why `customers` is kept despite the usual rule

Admin Dashboard OS normally skips `customers` when "customer" is only a role on
`User`. Here it is kept, because the backend exposes a dedicated
`/customers` endpoint returning **computed fields that do not exist on the user
record** — `orderCount`, `totalSpend`, `addressCount`. That is a genuinely
different question ("who are my best buyers?") from the Users directory ("find
this account"). Both already ship today.

### Skipped

| Module | Reason |
|---|---|
| `payments` | No `Payment` entity. Paystack state is a field on `Order` and is shown there. |
| `transactions` | No ledger. |
| `payouts` | No `Payout`/`Commission` entity, despite `platformFeePercent` existing. |
| `agents` | No courier/rider entity. |
| `organizations` | Not multi-tenant. |
| `media` | `VendorDocument` is a related list on Vendor, not a media library. |
| `content`, `moderation`, `notifications`, `reports` | No corresponding entities. |
| `roles-permissions` | `AdminRole` is a hardcoded Prisma enum, not a table. A matrix UI cannot write to it. The role model will be shown **read-only** in Settings instead. |
| **`audit-logs`** | **No `AuditLog` entity — this is a finding, not a note.** See §15. |

## 13. Integration strategy

- **Data.** Keep `lib/api.ts` / `adminFetch` exactly as-is. Add a
  `createAdminDataSource()` binding it to `ResourceDataSource`, mapping each
  endpoint's envelope key. No new fetch wrapper, no query library.
- **Auth.** `useAuth` re-exports the existing `useAdminSession()`. No second
  session source, no new dependency.
- **Permissions.** New `admin/permissions/` deriving `ROLE_GRANTS` from the real
  `AdminRole` ranks. Every grant gets a report row naming its server check.
- **Styling.** Rewrite `globals.css` as `tokens.css` + `admin.css`, keeping the
  4FG palette and moving all 83 stray colours onto tokens. Plain CSS — matching
  the project. No Tailwind, no CSS-in-JS.
- **Charts.** Use the **already-installed recharts** for the analytics module.
- **Routing.** No middleware added; the existing layout guard is kept and the
  permission layer sits on top of it.

   ever built. The refactor will **not** invent one.
